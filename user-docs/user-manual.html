adobe-downloader

Station10 internal tool — User Manual — September 2026

Overview

adobe-downloader is a Python command-line tool that downloads, transforms, and manages Adobe Analytics report data for Station10 clients. It replaces the earlier JavaScript codebase (downloadAdobeTableLocal) and handles everything from pulling ranked reports from the Adobe Analytics API through to producing analysis-ready CSV files.

Core abstraction

Everything the tool does is driven by a YAML config file. Each config file describes one job: what data to pull, which RSIDs to query, what date range to cover, and how to transform the output. Once the config is written and validated, running the job is a single command:

adobe-downloader run --config jobs/my_first_job.yaml

The tool is safe to interrupt and re-run. Every API request is tracked in a SQLite state database; completed requests are skipped automatically on resume so you never download the same file twice.

What it does end-to-end

  1. Loads and validates your YAML config against a strict Pydantic schema.
  2. Expands the job into individual API requests (one per RSID × date interval × report × segment).
  3. Downloads each request as a JSON file into <base_folder>/<client>/JSON/.
  4. Transforms each JSON file to a CSV using the configured transform type.
  5. Optionally concatenates all CSVs into a single output file and/or zips them.

Job types at a glance

job_typeWhat it does
report_downloadDownload ranked reports from the Adobe Analytics API for one or more RSIDs over a date range.
transform_concatTransform existing JSON files to CSV and concatenate them, without hitting the API.
segment_creationCreate Adobe Analytics segments from a CSV list of bot rules and share them with users.
lookup_generationBuild a dimension value → numeric item-ID lookup file used when constructing segment conditions.
rsid_updateFetch all report suites, download topline visit counts, and write filtered RSID list files.
compositeChain multiple steps (any combination of the above) into a single resumable pipeline.

Setup

Follow these steps in order the first time you use the tool. Setup takes about 15 minutes. Once it's done, day-to-day use is two terminals: one running the broker, one running jobs (see Everyday use).

How credentials work

The tool itself never holds Adobe credentials. Every API call goes to a small credential broker that runs on your own machine (broker/adobe_broker.py):

adobe-downloader  -->  broker on 127.0.0.1:8765  -->  Adobe Analytics API
                       (reads your OS keychain,
                        adds the access token)

You store your Adobe credentials once in your operating system's keychain (Credential Manager on Windows, Keychain on macOS). The broker reads them, gets an access token from Adobe, renews it automatically, and adds it to each request. The token and secret never appear in the repository, in logs, in the tool's output or to Claude.

Step 1 — Check the prerequisites

  • Python 3.12 or later. Check with python --version.
  • Git, and access to the AdobeBotAnalysis GitHub repository.
  • Access to the Adobe Developer Console project that holds the client's OAuth Server-to-Server credential, so you can read the client ID and secret. If you don't have it, ask the Adobe admin to add you as a developer on the project.
  • The project's service account must be assigned to an Adobe Analytics product profile. This is an admin task and is normally already done for existing clients.

Step 2 — Get the code and install it

Open a terminal (PowerShell on Windows, Terminal on macOS) and run:

git clone https://github.com/edwardgurton/AdobeBotAnalysis.git
cd AdobeBotAnalysis
python -m venv .venv

Activate the virtual environment. You need to do this in every new terminal you open for the tool:

# Windows (PowerShell)
.venv\Scripts\Activate.ps1

# macOS
source .venv/bin/activate

Your prompt now starts with (.venv). Install the tool together with the broker's extra dependency:

pip install -e ".[broker]"

Check it installed:

adobe-downloader --version

Windows: If PowerShell refuses to run Activate.ps1 with a message about execution policy, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once, then try again.

If adobe-downloader is not recognised as a command, use the python -m form instead. It works identically:

python -m adobe_downloader --version

Substitute python -m adobe_downloader for adobe-downloader in every command shown in this manual.

Step 3 — Collect your four Adobe values

Most of these come from the Adobe Developer Console: open Projects, choose the client's project, then open the OAuth Server-to-Server credential.

ValueKeychain keyWhere to find itSecret?
Client IDclient_idCredential page → Client IDNo
Client secretclient_secretCredential page → Retrieve client secretYes
Organization IDorg_idCredential page → Organization ID (ends in @AdobeOrg)No
Global company IDcompany_idNot shown in the Developer Console. Ask your Adobe Analytics admin or a colleague who already uses the tool. It's a short identifier, not a secret.No

Keep the Developer Console tab open. You'll paste each value straight into the next step. Don't save the secret in a text file, email or chat message.

Step 4 — Store the values in your keychain

In your activated terminal, run these four commands one at a time. Each one asks for a value:

python -m keyring set adobe-downloader-broker client_id
python -m keyring set adobe-downloader-broker client_secret
python -m keyring set adobe-downloader-broker org_id
python -m keyring set adobe-downloader-broker company_id

You'll see a prompt like Password for 'client_id' in 'adobe-downloader-broker':. Paste the value (right-click or Ctrl+V in PowerShell, Cmd+V on macOS) and press Enter.

Nothing appears when you paste. That's expected. The input is hidden so the value never shows on screen or in your shell history. If you think you pasted the wrong thing, just run the same command again; it overwrites the old value.

To check the entries exist without revealing them, open Credential Manager → Windows Credentials on Windows, or Keychain Access on macOS, and search for adobe-downloader-broker. You should see four entries. The real test is Step 5: the broker tells you exactly which entries, if any, are missing.

Step 5 — Start the broker

Open a second terminal, go to the repository folder, activate the virtual environment and start the broker:

cd AdobeBotAnalysis
.venv\Scripts\Activate.ps1          # macOS: source .venv/bin/activate
python broker/adobe_broker.py

If everything is set up correctly, you'll see two lines like these, and then the terminal waits:

2026-09-28 09:14:02,118 INFO obtained access token (valid for about 1439 min)
2026-09-28 09:14:02,120 INFO broker listening on http://127.0.0.1:8765

Leave this terminal open. The broker has to keep running while you use the tool. Each API request appears as one line, e.g. POST /reports -> 200. If it exits straight away with an error instead, see Troubleshooting. The message tells you what's wrong, such as which keychain entry is missing.

Security: Start the broker yourself, in your own terminal. Don't ask Claude or any other assistant to start it; the project's Claude settings deliberately block that. The broker only accepts connections from your own machine.

Step 6 — Check the tool can reach Adobe

Go back to your first terminal (the one not running the broker) and list the client's report suites:

adobe-downloader list-rsids --client Legend

You should see Found N report suite(s): followed by one line per report suite: the RSID, then its name. In the broker terminal, a matching GET /collections/suites -> 200 line appears.

Optionally, list the Analytics users visible to the client too:

adobe-downloader list-users --client Legend

To check the broker on its own, without the tool, open http://127.0.0.1:8765/_broker/health in a terminal:

# Windows (PowerShell)
Invoke-RestMethod http://127.0.0.1:8765/_broker/health

# macOS
curl http://127.0.0.1:8765/_broker/health

It reports status: ok and how long the current token has left. It never shows the token itself.

Step 7 — Run your first job

Jobs are YAML files. Create jobs/my_first_job.yaml; files directly in jobs/ are never committed to git. Paste this in:

job_type: report_download
client: Legend
description: "First run: topline metrics for one report suite, one week"

report_ref: toplineMetricsForRsidValidation

rsids:
  source: single
  single: "your-rsid-here"        # copy an RSID from the list-rsids output

interval: full

date_range:
  from: "2026-09-01"
  to: "2026-09-07"

transform:
  enabled: true
  type: summary_total
  concat: true

output:
  base_folder: "C:/Adobe_Downloads"  # any folder on your machine

Replace your-rsid-here with an RSID from the first column of the list-rsids output, and set base_folder to a folder you want output written to. Then check the config and run it in test mode:

adobe-downloader validate --config jobs/my_first_job.yaml
adobe-downloader run --config jobs/my_first_job.yaml --test

validate should end with Validation passed.. After run finishes, the downloaded JSON is in <base_folder>/Legend/JSON/ and the CSV in <base_folder>/Legend/CSV/. See Output folder layout for the full structure.

That's setup done. Next, read Key Concepts, then the example configs in jobs/examples/.

Before running the example configs: most examples refer to report suites by friendly name (e.g. Casinous) through the RSID list files in data/rsid_lists/. Translating those names needs a lookup file in data/report_suite_lists/, which isn't in git and is generated by the RSID Update flow. Check with a colleague before your first RSID update, because it also rewrites the shared RSID list files.

Everyday use

  1. Terminal 1: cd AdobeBotAnalysis, activate the virtual environment, then run python broker/adobe_broker.py. Leave it running.
  2. Terminal 2: cd AdobeBotAnalysis, activate the virtual environment, then run your jobs.
  3. When you're finished, press Ctrl+C in terminal 1 to stop the broker.

The broker renews its token automatically, so it can stay running all day. If you use Claude Code with this project, start the broker yourself before asking Claude to run jobs; Claude can use the running broker but can't start it.

Changing the secret

When the client secret is rotated in the Developer Console, run python -m keyring set adobe-downloader-broker client_secret again with the new value, then stop the broker (Ctrl+C) and start it again.

Using a different port

If port 8765 is already in use, start the broker with python broker/adobe_broker.py --port 9000. Then, in the terminal where you run jobs, tell the tool where to find it:

# Windows (PowerShell) - lasts for this terminal session
$env:ADOBE_API_BASE_URL = "http://127.0.0.1:9000"

# macOS
export ADOBE_API_BASE_URL=http://127.0.0.1:9000

Where to run commands from

Always run adobe-downloader from the repository root. The tool resolves data/ paths relative to the current working directory, so running from a different location will cause file-not-found errors.

Key Concepts

Jobs and YAML configs

A job is a single unit of work described by a YAML file. The job_type field at the top of the file determines what the job does and which fields are valid. Config files live in jobs/ — use jobs/templates/ as starting points and jobs/examples/ to see real worked examples for the Legend client.

RSIDs

An RSID (Report Suite ID) is Adobe's identifier for a report suite. The tool accepts RSIDs in three ways, controlled by the rsids.source field:

sourceHow RSIDs are supplied
singleOne RSID written directly in the config (rsids.single).
listA YAML list of RSIDs written in the config (rsids.list).
fileA plain-text file with one RSID per line (rsids.file). See below for file format.

RSID list files

RSID list files in data/rsid_lists/ contain one entry per line. Lines beginning with # are comments. Each non-comment line is a plain RSID clean name (the human-readable name used internally, not the raw Adobe rsid string):

# Minimum threshold = 1000
# Date range = 2025-01-01 to 2025-01-31
OnlineBettingcom
MarcadoresOnlinecom
Casinoorg

These files are generated automatically by the rsid_update flow (see RSID Update) and should not normally be edited by hand.

Report definitions

A report definition specifies what to request from the Adobe API: a dimension, a list of metrics, optional segments, and a row limit. Definitions live in report_definitions/ as YAML files and are organised into groups. You reference them in a config using either:

  • report_ref: <name> — one named report from the registry
  • report_group: <group> — all reports in a group (downloads them all)
  • report: — an inline definition written directly in the config (for one-off reports)

See Report Definitions for the full list of available groups and reports.

Date intervals

The interval field controls how the date range is split into individual API requests:

  • full — one request covering the entire date range
  • month — one request per calendar month within the range
  • day — one request per day (produces many files; use with care)

Most bot investigation work uses month to get monthly breakdowns.

State database and resume

When a report_download job starts, a SQLite database is created at:

<output.base_folder>/<client>/state/<job_id>.db

Every request is recorded as pending before it runs and updated to completed or failed afterward. If the job is interrupted, re-running the same command resumes from where it left off. Completed requests are skipped. Use --no-resume to force a fresh start.

Transform types

JSON files are converted to CSV using a transform type that knows the structure of the downloaded data. This conversion is not automatic on a standalone report_download job — that job type only downloads. To transform and concatenate afterward, either run adobe-downloader transform manually, or add a transform_concat step to a composite job.

typeUsed for
standardGeneric ranked-report output. Suitable for most one-off reports.
bot_investigationBot investigation reports (adds botRuleName, rsid columns).
bot_validationBot validation reports with per-rule segment iteration.
bot_rule_compareSide-by-side comparison of bot rule variants.
final_bot_metricsAnnual final bot metrics summary.
summary_totalTopline totals (visitors, visits) with no dimension breakdown.

Output folder layout

All output is written under output.base_folder/<client>/:

<base_folder>/
  <client>/
    JSON/          raw downloaded JSON files
    CSV/           transformed CSV files
    state/         SQLite state databases
    config_archive/  copies of the config file saved after each run
    job_history.jsonl  append-only run history log

If output.job_name is set, an extra folder for that name is inserted between the client and JSON/CSV, so downloads from different investigations don't mix in the same folder:

<base_folder>/
  <client>/
    <job_name>/
      JSON/
      CSV/

See Composite Jobs → Naming with job_name for how this also affects the name of the final concatenated CSV.

Running Jobs

The run command

The primary command for executing any job:

adobe-downloader run --config <path-to-config.yaml>
FlagDefaultDescription
--config / -crequiredPath to the job YAML config file.
--report / -rNoneDownload only this one named report (overrides report_group expansion).
--no-resumeFalseIgnore existing state and re-download everything from scratch.
--testFalseEnable test mode: caps RSIDs, date intervals, and segments per test_limits config. See Test Mode.

validate

Parse and schema-check a config file without running any downloads. Always run this first when writing a new config.

adobe-downloader validate --config jobs/my_first_job.yaml
FlagDefaultDescription
--config / -crequiredPath to the config file to validate.

Exit codes: 0 = valid, 1 = schema error, 2 = valid schema but referenced files missing.

status

Print the current state of a report_download job (completed / pending / failed counts).

adobe-downloader status --config jobs/my_first_job.yaml

retry

Re-queue failed (or all non-completed) requests so they will be attempted on the next run.

adobe-downloader retry --config <config.yaml> [--failed-only]
FlagDescription
--failed-onlyRe-queue only requests with status failed. Omitting this flag re-queues all non-completed requests.

reset

Delete all state for a job so it starts completely fresh. Requires --confirm.

adobe-downloader reset --config <config.yaml> --confirm

validate-output

Check that all expected output files exist and are non-empty after a download job.

adobe-downloader validate-output --config <config.yaml> [--dry-run] [--retry]
FlagDescription
--dry-runReport missing files without re-downloading.
--retryRe-download any missing or empty files immediately.

history

Show recent job runs from the append-only job history log.

adobe-downloader history --client Legend [--last 10] [--status completed] [--since 2025-06-01]

transform

Transform JSON files to CSV and optionally concatenate them, without touching the API. Useful if a transform step failed after a successful download.

adobe-downloader transform \
  --json-dir "/path/to/output/Legend/JSON" \
  --pattern "Legend_botInvestigation*.json" \
  --concat \
  --concat-output "/path/to/output.csv"

cleanup

Remove old processed files. Always requires --confirm to actually delete.

adobe-downloader cleanup \
  --client Legend \
  --older-than 30d \
  --type processed-json \
  --confirm

Valid --type values: processed-json, logs, state.

Flow: Report Download

The report_download job type is the workhorse of the tool. It iterates over RSIDs, date intervals, and optionally segments, sending one ranked-report API request per combination and saving the result as a JSON file.

Minimal example

job_type: report_download
client: Legend
description: "Download bot investigation reports for Jan 2025"

report_group: bot_investigation

rsids:
  source: file
  file: data/rsid_lists/legend_investigation.txt
  batch_size: 12

interval: month

date_range:
  from: "2025-01-01"
  to: "2025-01-31"

transform:
  enabled: true
  type: bot_investigation
  concat: true

resume: true

output:
  base_folder: "/Users/edwardgurton/Documents/Work/Adobe Downloads"

RSID sources

Choose one of the three rsids.source values:

# From a file (most common for multi-RSID jobs)
rsids:
  source: file
  file: data/rsid_lists/legend_investigation.txt
  batch_size: 12  # max concurrent API requests for this job/step

# Explicit list
rsids:
  source: list
  list:
    - trillioncoverscom
    - casinoorg

# Single RSID
rsids:
  source: single
  single: trillioncoverscom

Date intervals

date_range:
  from: "2025-01-01"
  to: "2025-03-31"

interval: month   # full | month | day

Using month with the above range produces three intervals: January, February, and March 2025. The full interval makes one request covering the entire range.

Report specification

Exactly one of report_ref, report_group, or report must be set:

# Named report from the registry
report_ref: botInvestigationMetricsByBrowser

# All reports in a group
report_group: bot_investigation

# Inline definition (for one-off or experimental reports)
report:
  name: myCustomReport
  dimension: variables/daterangeday
  row_limit: 500
  segments:
    - s3938_61bb0165a88ab931afa78e4c
  metrics:
    - metrics/visitors
    - metrics/visits
    - metrics/event3
  csv_headers: [id, day, unique_visitors, visits, raw_clickouts, fileName, fromDate, toDate]

Segment iteration

When segments is set, the tool downloads a separate copy of each report for each segment ID. This is how bot validation works — one download per bot rule segment. See Segments for all source options.

segments:
  source: segment_list_file
  file: data/segment_lists/Legend/Apr25-RoundFive.json

Transform options

transform:
  enabled: true
  type: bot_investigation   # see table in Concepts
  concat: true              # concatenate all CSVs into one file after transform

post_processing:
  delete_json_after_transform: false   # set true to save disk space
  zip_csvs_after_concat: true          # zip the concat output

File naming

Output JSON files follow this naming convention:

<client>_<reportName>[_<extra>][_DIMSEG<segmentId>_]_<fromDate>_<toDate>.json

Use file_name_extra to add a label to the filename (useful for distinguishing parallel runs):

file_name_extra: "Coverscom-FullRun"

When segments.source: segment_list_file is used, each segment's own sanitized name is merged into its filename automatically, as a RULE<name> anchor — e.g. Legend_botFilterExcludeMetricsByMonth_Casinoorg_RULEUS-Mobile-Bots_2026-01-01_2026-01-31.json. The raw segment ID (DIMSEG<segmentId>) is not included by default — set include_segment_id_in_filename: true if you also need it embedded.

Flow: Transform and Concatenate

The transform_concat job type transforms existing JSON files to CSV and concatenates them. No API calls are made. Use this when:

  • A transform step failed after a successful download and you want to re-run it.
  • You want to apply a different transform type to already-downloaded data.
  • You need to concatenate a subset of files matching a specific pattern.

Example

job_type: transform_concat
client: Legend
description: "Re-transform existing JSON files for bot investigation Q1 2025"

transform:
  enabled: true
  type: bot_investigation
  source_pattern: ".*botInvestigationMetricsByBrowser.*2025-01.*\.json$"
  source_folder: null    # null = default JSON folder for this client
  output_subfolder: null
  concat: true

concat:
  enabled: true
  file_pattern: ".*\.csv$"
  custom_headers: null   # override column headers by index if needed
  # file_name_extra: "<label>"   # inserted right after job_name in the output filename

output:
  base_folder: "/Users/edwardgurton/Documents/Work/Adobe Downloads"

When to use inline transform vs. transform_concat

If you are doing a full download, use the transform block inside a report_download config. The transform_concat job type is for standalone re-processing after the download is already complete.

Concat options

FieldTypeDescription
concat.enabledboolWhether to run concatenation after transform.
concat.file_patternstring (regex)Regular expression selecting which CSV files to include. Default: .*\.csv$.
concat.custom_headersmapOverride column headers by 1-based column index. Example: 1: "MyColumn".
concat.file_name_extrastring or nullOptional label spliced into the concatenated output's filename, right after job_name. See Naming with job_name.

Transform via CLI (no config file)

For a quick ad-hoc transform, use the transform command directly:

adobe-downloader transform \
  --json-dir "/path/to/Legend/JSON" \
  --pattern "Legend_botInvestigationMetricsByBrowser*.json" \
  --concat \
  --concat-output "/path/to/output.csv"

Flow: Segment Creation

The segment_creation job type reads a CSV list of bot rules, creates the corresponding segments in Adobe Analytics via the API, and writes three output files used by downstream validation jobs.

Example config

job_type: segment_creation
client: Legend
description: "Create Apr25 bot rule segments and share with Legend user"

segment_creation:
  input_csv: data/segment_creation_lists/Apr25-RoundFive.csv
  share_with_users:
    - "200419062"     # Adobe user ID (numeric string)
  test_mode_row: null # set to a row number (1-based) to test just one row

output:
  base_folder: "/Users/edwardgurton/Documents/Work/Adobe Downloads"

Input CSV format

The input CSV must have the following columns, with these exact header names in the header row (parsed via csv.DictReader, so the names must match verbatim):

ColumnValuesDescription
CompareValidateCompare, Validate, Compare - Special, Validate - SpecialDetermines which output list the segment appears in.
SegmentNamestringHuman-readable segment name (also used to derive the bot rule name).
RSIDCleanNamestringClean name of the report suite the segment is scoped to. Ignored on - Special rows.
Dimension1friendly nameFirst dimension for the segment condition (e.g. BrowserType). On Compare rows, this value is also written to reportToIgnore in the compare list — see reportToIgnore and multi-dimension rules below (Compare rows only — reportToIgnore isn't written for Validate rows at all, since bot_validation never reads it).
Dimension1ItemstringValue to match for dimension 1. Ignored on - Special rows.
Dimension2friendly name or blankOptional second dimension condition. Ignored on - Special rows. When set on a Compare row, this dimension is also added to reportToIgnore alongside Dimension1.
Dimension2Itemstring or blankRequired if Dimension2 is set. Ignored on - Special rows.
Dimension3friendly name or blankOptional third dimension condition. Requires Dimension2 to be set first — validation fails otherwise. Ignored on - Special rows. This column may be omitted entirely from older, 2-dimension input files.
Dimension3Itemstring or blankRequired if Dimension3 is set. Ignored on - Special rows.
Dimension4friendly name or blankOptional fourth dimension condition. Requires Dimension3 to be set first — validation fails otherwise. Ignored on - Special rows. This column may be omitted entirely from older, 2-dimension input files.
Dimension4Itemstring or blankRequired if Dimension4 is set. Ignored on - Special rows.

Dimensions that require a numeric lookup (such as BrowserType, OperatingSystem, MobileManufacturer, MonitorResolution) are automatically resolved using the lookup files in data/lookups/.

reportToIgnore and multi-dimension rules

Because a rule's segment is built from Dimension1 (and optionally Dimension2-Dimension4), comparing that same dimension's report back against the segment is tautological — the report was the reason the rule exists. reportToIgnore in the compare list tells bot_rule_compare which report(s) to skip for each rule:

  • Single-dimension row (Dimension2 blank) → reportToIgnore is just Dimension1, e.g. BrowserType.
  • Multi-dimension row (Dimension2, and optionally Dimension3/Dimension4, set) → reportToIgnore holds every set dimension, |-joined in tier order, e.g. OperatingSystem|BrowserType or OperatingSystem|BrowserType|Domain|MobileManufacturer. All of those reports are skipped when the rule is compared.

This is generated automatically by segment_creation — nothing to configure here. It matters when you're hand-editing a compare CSV or writing an inline bot_rules: block for a bot_rule_compare step; see bot_rules (bot_rule_compare) in the YAML Field Reference for the exact accepted formats (short name, full report name, |-delimited string, or a YAML list).

Dimension1 through Dimension4 must each be one of the following friendly names (on non-Special rows — any other value raises an error before segment creation). Up to 4 dimensions may be AND'ed together in a single segment; dimensions must be filled in tier order (2 before 3, 3 before 4).

Friendly name(s)Adobe variableNeeds numeric lookup?
PageURL, Page URLvariables/evar2No
Domainvariables/filtereddomainNo
UserAgent, User Agentvariables/evar23No
Region, Regionsvariables/georegionYes
OperatingSystem, OperatingSystems, Operating System, Operating Systemsvariables/operatingsystemNo
MonitorResolution, Monitor Resolutionvariables/monitorresolutionYes
MobileManufacturer, Mobile Manufacturervariables/mobilemanufacturerNo
MarketingChannel, Marketing Channelvariables/marketingchannelYes
BrowserType, Browser Typevariables/browsertypeYes
ReferringDomain, Referring Domainvariables/referringdomainNo
Country, Countriesvariables/geocountryYes

This whitelist is defined in data/segment_creation_dimensions.yaml, loaded at runtime by adobe_downloader/segments/create_segment.py. Add a new dimension with:

adobe-downloader add-dimension --name Country --name Countries \
  --adobe-variable variables/geocountry --requires-lookup

--name may be repeated to register aliases; --requires-lookup marks a dimension whose values are numeric IDs, which then needs a data/lookups/<cleaned-variable>/lookup.txt file (populate one with a lookup_generation job, or by hand). The command refuses to overwrite an existing name — edit data/segment_creation_dimensions.yaml directly to change or remove one.

Compare - Special / Validate - Special rows skip the Adobe API call entirely — the placeholder segment ID UPDATE-SEGMENT-ID is written to the output CSV instead, for cases where the segment already exists and just needs to be added to the compare/validate list by hand.

Bot rule numbers and tagging. Unless renumber_validates: false is set, the job looks up the highest bot rule number among segments tagged BotRuleCandidates and numbers every Validate and Validate - Special row from the next one up, in list order. You no longer need to look the number up by hand. Each Validate segment the job creates is tagged BotRuleCandidates. Validate - Special rows get a number too, and the job lists their final names at the end: create each one in Adobe under exactly that name, tag it BotRuleCandidates yourself (the API can't tag segments it doesn't own), then put its segment ID in place of UPDATE-SEGMENT-ID in the validate CSV. Any created segment that couldn't be tagged is listed as NOT TAGGED; tag those in Adobe.

A ready-to-copy example with both single- and dual-condition rows is checked into the repo at jobs/inputs/segment_creation_lists/segmentCreationTemplate.csv.

Finding the next bot rule number

Validate segments are named NNNN BOT RULE: …, where NNNN is a 4-digit bot rule number, and carry the Adobe tag BotRuleCandidates. Before you build a new segment creation list, look up the highest number already in use:

adobe-downloader bot-rule-number --client Legend          # highest number in use, e.g. 256
adobe-downloader bot-rule-number --client Legend --next   # next free number, e.g. 257

The command prints only the integer, so you can paste it straight into the Bot Rule Compare workbook (SegmentCreationList_Final!B4) instead of searching Adobe by hand.

  • It looks at every segment tagged BotRuleCandidates and reads the first 4 characters of each name. Names that don't start with exactly 4 digits (for example BOTCOMPARE_… or 12 BOT…) are ignored. If none match, it prints 0.
  • It asks Adobe for all users' segments (includeType=all, which needs admin rights). If Adobe refuses, it falls back to your own segments plus those shared with you (includeType=shared) and logs a warning. In that case, segments owned by colleagues and not shared with you are not counted.
  • A segment only counts if it is tagged. An untagged validate segment's number can be reused.
  • The numbers are housekeeping. Nothing stops two people taking the same number at the same time.
  • Use --tag NAME to search a different tag. The default comes from segment_creation.candidate_tag.

Like every Adobe call, this needs the local credential broker to be running.

Flow: Lookup Generation

A lookup file maps human-readable dimension values (e.g. "Chrome 120") to the numeric item IDs used internally by Adobe Analytics. These IDs are required when creating segment conditions for dimensions like Browser, BrowserType, OperatingSystem, MobileManufacturer, and MonitorResolution. Lookup files are stored in data/lookups/<dimensionName>/lookup.txt.

When do you need to regenerate a lookup?

If segment_creation reports that a value cannot be found in the lookup, the lookup file is probably stale (new dimension values have appeared since it was last generated). Regenerate it using a recent date range.

Example config

job_type: lookup_generation
client: Legend
description: "Generate browser dimension lookup for trillioncoverscom (Jan 2025)"

lookup_generation:
  dimension: variables/browser     # Adobe dimension variable string
  rsid: trillioncoverscom
  segments:
    - s3938_61bb0165a88ab931afa78e4c  # Optional: filter the lookup request
  output_file: null                   # null = auto-named in data/lookups/

date_range:
  from: "2025-01-01"
  to: "2025-01-31"

output:
  base_folder: "/Users/edwardgurton/Documents/Work/Adobe Downloads"

Searching a lookup file

To check what ID a specific value maps to (useful for debugging segment conditions):

adobe-downloader search-lookup --dimension BrowserType --value "Chrome Mobile"

If the value is not found exactly, the command shows similar entries.

Flow: RSID Update

The rsid_update flow refreshes the two RSID list files used by investigation and validation jobs. It fetches all report suites for the client, downloads a topline visit count for each, and writes filtered lists based on configurable thresholds.

Run this before starting a new investigation cycle to ensure the RSID lists reflect the current set of active report suites.

Example config

job_type: rsid_update
client: Legend
description: "Refresh Legend RSID lists — run before each new investigation"

rsid_update:

  validation_threshold: 1000     # minimum visits to include in validation list
  include_virtual: false         # exclude virtual report suites (rsid prefix: vrs_)

date_range:
  from: "2025-01-01"
  to: "2025-01-31"

output:
  base_folder: data/rsid_lists/

Flow: Composite Jobs

A composite job chains multiple steps into a single resumable pipeline. Each step can reference the outputs of previous steps, making it possible to run segment creation, download, validate, and transform in sequence with a single command.

Example: full bot investigation pipeline

job_type: composite
client: Legend
description: "Full Legend bot investigation: segment creation + download + validate + transform"

date_range:
  from: "2025-01-01"
  to: "2025-03-31"

output:
  base_folder: "/Users/edwardgurton/Documents/Work/Adobe Downloads"

steps:
  - step: segment_creation
    id: create_segments
    segment_creation:
      input_csv: data/segment_creation_lists/Apr25-RoundFive.csv
      share_with_users:
        - "200419062"

  - step: report_download
    id: download_investigation
    report_group: bot_investigation
    rsids:
      source: file
      file: data/rsid_lists/legend_investigation.txt
      batch_size: 12
    segments:
      source: step_output
      step_id: create_segments
      output_key: segment_list_file
    interval: month

  - step: validate_output
    id: validate
    depends_on: download_investigation
    config_ref: download_investigation
    retry: true

  - step: transform_concat
    id: transform
    depends_on: validate
    transform:
      type: bot_investigation
      concat: true

Step types

stepDescription
report_downloadDownload reports from the Adobe API.
transform_concatTransform JSON files to CSV and concatenate.
segment_creationCreate segments from a CSV list.
validate_outputCheck all expected output files exist; optionally re-download missing ones.
rsid_updateRefresh RSID list files.
dim_to_segmentsGenerate segments from dimension values automatically.
lookup_generationBuild a dimension lookup file.
bot_rule_compareRun a bot rule comparison analysis.

Naming output with job_name

Set output.job_name on the composite job to give an investigation a consistent, human-readable name across its folder structure and final output file:

output:
  base_folder: "C:/Adobe_Downloads"
  job_name: "casinoorg_seo_homepage_bot_investigation_90d"

This does two things:

  • Every report_download, bot_rule_compare, and final_bot_metrics step writes JSON/CSV under a <job_name>/ subfolder instead of directly under the client folder (see Output folder layout).
  • A transform_concat step's final concatenated CSV is named with a prefix from its transform.type, and written into that same <job_name>/ folder:
transform.typePrefix
bot_investigationINVESTIGATION_
bot_validationVALIDATION_
bot_rule_compareCOMPARE_
final_bot_metricsFINALMETRICS_
standardREPORT_
summary_totalSUMMARY_

For example, the config above with a transform_concat step of type: bot_investigation produces:

C:/Adobe_Downloads/Legend/casinoorg_seo_homepage_bot_investigation_90d/JSON/...
C:/Adobe_Downloads/Legend/casinoorg_seo_homepage_bot_investigation_90d/CSV/...
C:/Adobe_Downloads/Legend/casinoorg_seo_homepage_bot_investigation_90d/INVESTIGATION_casinoorg_seo_homepage_bot_investigation_90d.csv

If output.job_name is left unset, the transform_concat step falls back to naming its output <step_id>_concat.csv in the CSV folder — e.g. a step with id: transform produces the generic transform_concat.csv. Always set job_name to get a meaningful, distinguishable output file.

Adding a custom label with concat.file_name_extra

A transform_concat step's concat: block can set file_name_extra to splice a free-text label into the output filename, immediately after job_name:

  - step: transform_concat
    id: transform
    transform:
      type: bot_investigation
    concat:
      enabled: true
      file_name_extra: "MyLabel"

This turns INVESTIGATION_casinoorg_seo_homepage_bot_investigation_90d.csv into INVESTIGATION_casinoorg_seo_homepage_bot_investigation_90d_MyLabel.csv. If the step's transform.split_by_bot_rule is also set, the label lands between job_name and the per-rule name (e.g. COMPARE_<job_name>_MyLabel_<ruleName>.csv). It also works with the no-job_name fallback above, producing <step_id>_MyLabel_concat.csv.

file_name_extra is optional — leaving it unset, blank, or whitespace-only produces the same filename as if it weren't there at all. Characters illegal in Windows filenames (<>:"/\|?*) are replaced with -. Like job_name, a long value eats into the same Windows 260-character path limit, so keep it short.

depends_on

Use depends_on: <step_id> to ensure a step only runs after its dependency has completed successfully. If the dependency has not completed, the pipeline halts with an error.

Inter-step output references

Use source: step_output to wire one step's output into another step's input:

segments:
  source: step_output
  step_id: create_segments        # id of the earlier step
  output_key: segment_list_file   # key in that step's output dict

Common output keys for segment_creation steps:

output_keyContent
segment_list_filePath to the JSON file listing all created segment IDs.
compare_list_filePath to the Compare bot rules list.
validate_list_filePath to the Validate bot rules list.

Common output keys for rsid_update steps:

output_keyContent

Resume across steps

Composite jobs are fully resumable. If the pipeline is interrupted mid-way, re-running the same command skips all already-completed steps and resumes from the first incomplete one. The state for each step is stored in the same SQLite database as the overall composite job.

test_mode in composite jobs

Set test_mode: true at the top level of a composite config, or pass --test on the CLI. The test limits apply to all report_download steps in the composite.

Test Mode

Test mode limits the number of RSIDs, date intervals, and segments processed so you can verify a config works end-to-end without triggering hundreds of API requests. Always use test mode the first time you run a new config.

Enabling test mode

Either set it in the config file:

test_mode: true
test_limits:
  max_rsids: 2
  max_date_intervals: 1
  max_segments: 2

Or pass --test on the CLI (overrides the config setting):

adobe-downloader run --config jobs/my_first_job.yaml --test

Recommended test config settings

SettingRecommended test valueReason
test_limits.max_rsids2Enough to verify iteration logic without a large API bill.
test_limits.max_date_intervals1One month is sufficient to check the full data pipeline.
test_limits.max_segments2Enough to verify segment iteration.
resumefalseStart fresh on each test run so you see a clean result.
transform.concatfalseToo few files to make concatenation useful.

What test mode does not limit

Test mode only caps the iteration counts. It does not change the API endpoint, authentication, or report definitions. The requests that are sent are real Adobe Analytics API calls.

Important: Test mode limits are applied in the order RSIDs/intervals/segments are iterated. The first N items are used; there is no random sampling. Check that the first few items in your RSID file and segment list are representative before running in test mode.

Debug Mode

Add --debug to any run or validate-output command to get full API transparency — every request sent and every error response received is printed to the console.

adobe-downloader run --config jobs/casinoorg_seo_homepage_bot_investigation_90d_full.yaml --debug
adobe-downloader validate-output --config jobs/... --retry --debug

What gets printed

For every API call (GET and POST):

  • Method + URL
  • Request body (POST only) — pretty-printed JSON, capped at 20 000 characters.

On any HTTP error (4xx or 5xx):

  • Response status + reason phrase
  • Full response body — Adobe's error message, capped at 20 000 characters. This is the most useful piece when diagnosing 403 / 400 errors.

Silent file log

The same DEBUG information is also written to the rotating log file at <base_folder>/<client>/.logs/<config-stem>.log on every run, regardless of whether --debug is passed. If a job has already failed, check the log file before re-running with --debug.

Diagnosing 403 errors on composite jobs

A common source of confusion: a composite job fails with a 403 error, but a standalone report_download job using the same parameters succeeds.

This happens because the composite job runner executes a pre-flight metric validation step before each report_download step. The preflight makes one additional probe API request per RSID (1 row, 1 day, all metrics in the report group). If any metric is not accessible for the RSID — or if the probe request itself triggers a permission error — the job stops before downloading anything.

Run with --debug to see the preflight probe body and Adobe's exact error response:

adobe-downloader run --config jobs/casinoorg_seo_homepage_bot_investigation_90d_full.yaml --debug

Token security: Debug output never includes request headers. Auth headers are added by the local broker, so the tool never sees a token to print.

Troubleshooting

Schema validation failed

Symptom: adobe-downloader run or validate prints Schema validation failed with field names and error messages.

Cause: A required field is missing, a value has the wrong type, or a mutually exclusive combination is set (e.g. both report_ref and report_group).

Fix: Read the error message carefully. The field path (e.g. rsids -> source) tells you exactly what is wrong. Run validate after every edit until it passes.

Cannot reach the credential broker

Symptom: Cannot reach the Adobe credential broker at http://127.0.0.1:8765.

Fix: The broker isn't running, or is running on a different port. Start it in a separate terminal and leave it running (Setup step 5). If you started it with --port, set ADOBE_API_BASE_URL to match (Using a different port).

Broker exits: missing keychain entries

Symptom: missing keychain entries under service 'adobe-downloader-broker': org_id, company_id (or similar).

Fix: The listed entries were never stored, or were stored under a different name. Re-run the python -m keyring set adobe-downloader-broker <key> command for each listed key (Setup step 4). Key names are case-sensitive.

Broker exits: IMS token failure

Symptom: token request to Adobe IMS failed (HTTP 400) or (HTTP 401) at startup, or HTTP 502 with the same message while jobs are running.

Fix: Adobe rejected the client ID or secret. The usual causes are a typo when pasting, or a secret that has been rotated. Store both values again (Setup step 4) and restart the broker.

Broker exits: keyring is not installed

Symptom: the 'keyring' package is not installed, or No module named keyring when storing values.

Fix: The virtual environment isn't active, or the broker extra wasn't installed. Activate .venv and run pip install -e ".[broker]" (Setup step 2).

Broker won't start: address already in use

Symptom: the broker exits with OSError mentioning the address or port already being in use.

Fix: Another broker is probably already running in a different terminal, so use that one. Otherwise, start it on another port and set ADOBE_API_BASE_URL (Using a different port).

403 Forbidden from Adobe on every request

Symptom: the broker starts fine, but requests fail with HTTP 403 and the broker logs lines like GET /collections/suites -> 403.

Fix: The token is valid, but the service account isn't allowed to use Analytics for this company. Check the company_id keychain entry is right. Then ask the Adobe admin to confirm the project's service account is assigned to an Analytics product profile. (A 403 on only some requests is different; see Debug Mode.)

RSID file not found

Symptom: RSID file not found: data/rsid_lists/legend_investigation.txt.

Fix: Run adobe-downloader update-rsids (or a composite job with an rsid_update step) to generate the RSID list files. Also verify you are running from the repository root.

Segment list file not found

Symptom: Segment list file not found: data/segment_lists/Legend/....

Fix: Run the segment_creation job first to generate the file, or update the segments.file path to point to an existing file.

Config has changed since the last run

Symptom: Warning on run: config has changed since the last run.

Cause: The YAML file was modified after the job's state database was created. The state is keyed to the config hash.

Fix: If the change was intentional and you want to continue the previous download with the new config, proceed normally. If you want to start completely fresh, run with --no-resume or use the reset command.

Many failed requests

Symptom: status shows a large number of failed requests.

Cause: Adobe API rate limits, temporary network issues, or invalid segment/metric IDs.

Fix:

  1. Check the last errors shown by adobe-downloader status --config <config>.
  2. If rate-limited, lower rsids.batch_size (e.g. to 6) and re-run.
  3. Run adobe-downloader retry --config <config> --failed-only to re-queue failed requests.
  4. Run adobe-downloader run --config <config> again to process the re-queued requests.

Lookup value not found during segment creation

Symptom: Segment creation errors with Value 'X' not found in lookup.

Fix:

  1. Use adobe-downloader search-lookup --dimension <dim> --value <value> to search the lookup for similar entries.
  2. If the value genuinely does not exist in the lookup, regenerate the lookup file using a recent date range (see Lookup Generation).
  3. Check spelling and case. MonitorResolution values are normalised (e.g. 1920x1080 becomes 1920 x 1080).

No RSID lookup file found in data/report_suite_lists

Symptom: segment_creation aborts with No RSID lookup file found in data/report_suite_lists.

Fix: Run rsid_update to generate a dated pairs file in data/report_suite_lists/.

validate-output finds missing files after a completed run

Symptom: validate-output reports missing JSON files even though the job showed as completed.

Fix: Run adobe-downloader validate-output --config <config> --retry to re-download missing files automatically.
